# Prompt Audit — Sprint 6.14

Pre-launch audit of every AI prompt in `backend/app/prompts/`. The
goal: confirm each prompt follows `.claude/rules/ai-prompts.md` and
identify weak spots before launch.

**Scope**: 9 prompts, all `v1` at the time of audit.

**Method**: structural review against the rules + fixture coverage
review. No live model invocation — that requires Azure OpenAI quota
and lands in a follow-up eval pass once a real-Azure run is
scheduled (mirrors the Sprint 2 / 3 pattern where the smoke runs
caught latent issues the unit tests couldn't surface).

## TL;DR

Every prompt passes the audit. No tightenings required for launch.
Five regression-eval fixtures per prompt now ship under
`backend/app/prompts/fixtures/`; the structural test
`tests/unit/prompts/test_fixtures.py` keeps the fixture contract
honest in CI.

## Per-prompt scorecard

Each prompt is scored on the seven rules from
`.claude/rules/ai-prompts.md`:

1. **Version comment** — `# v1.0 — <date> — <description>` at top
2. **System / user split** — `[SYSTEM]` and `[USER]` sections
3. **Strict JSON output** — schema + first/last char rules
4. **Source-only constraint** — explicit "do NOT invoke outside knowledge"
5. **Insufficient-source escape** — `{"insufficient_source": true}` branch
6. **Difficulty calibration** — per-difficulty guidance where applicable
7. **Anti-slop language** — negative constraints, no vague "good question"

A check (✓) means the rule is honoured cleanly; a dash (—) means the
rule doesn't apply to that prompt.

## Strengths across the suite

* **Explicit JSON envelope rules** — every prompt requires "first
  char `{`, last char `}`" so a stray "Here is your question:"
  preamble would fail the parser fast. Sprint 3.8's safety review
  builds on this.
* **Difficulty calibration with examples** — the three-tier
  (beginner / intermediate / advanced) is consistent across all five
  question prompts. The examples ("Find the area of a rectangle…",
  "Compare and contrast…") anchor the model's interpretation.
* **Dedup guidance** — every question/flashcard prompt accepts a
  `seen_*` list and is instructed to return `insufficient_source` if
  natural variations are exhausted. Prevents the dreaded "same
  question rephrased five times" pattern.
* **Negative constraints in dedicated sections** — not buried in
  paragraphs but called out as Field Rules / Content Rules. Models
  follow these much more reliably than scattered hints.

## Risks the audit can't catch

The structural audit can't validate the *quality* of generated output
— that requires a real-Azure run with diverse fixtures (which is
what the fixture files now enable). Open risks until that run:

* **Distractor plausibility** in MCQ. The prompt instructs
  "plausible but unambiguously wrong"; without an eval run we don't
  know if GPT-4o actually produces plausible distractors or
  degenerate ones ("None of the listed planets is the answer.").
* **Long-answer rubric key-points coverage**. The prompt requires
  key_points to appear in reference_answer. Worth checking the
  reverse: does GPT-4o ever produce a reference_answer that
  *exceeds* the key_points (extra ideas that should grade
  correct but won't because they're not in the rubric)?
* **Math LaTeX consistency**. The prompt allows both `$...$` and
  plain digits for "pure numeric" answers. Borderline cases (e.g.
  `0.5` vs `$\frac{1}{2}$`) could vary across runs and confuse the
  Sprint 3.10 evaluator's normalisation pass.

These are eval-run findings, not prompt-rewrite findings — they go
on the Sprint 6 / launch ramp-up backlog, not this commit.

## How to run the eval (post-launch)

1. The fixtures under `backend/app/prompts/fixtures/<prompt>.json`
   are the inputs. Each file has 5+ cases covering happy / short /
   long / cross-subject / ambiguous.
2. Invoke the `/prompt-eval` skill (see
   `.claude/skills/prompt-eval/SKILL.md`) with the prompt name.
   The skill runs each fixture through the OpenAI service and
   writes a markdown report under `docs/prompt-evals/<prompt>-<date>.md`.
3. When a prompt changes, re-run before merging. A new version (v2)
   means a new template file; the fixture file keeps its name
   (`question_mcq.json`) so the eval can compare v1 vs v2 outputs
   on the same inputs.

The structural test (`tests/unit/prompts/test_fixtures.py`) keeps
the fixture contract honest in CI — missing key, missing case,
typo'd input variable, all fail loudly.
